# DeepCode

English | [中文](README.zh.md)

**DeepCode is an unofficial community desktop client for DeepSeek Harness. It is not affiliated with or endorsed by DeepSeek.** The Harness runtime and the official Web UI are DeepSeek's work; DeepCode is See-Sol-Lab's product layer built on top of them.

DeepCode Desktop is the Windows host and distribution for the DeepCode product: the Desktop Chrome control layer, the native Harness control plane (Managed/Existing Home, profile discovery and switching, last-known-good recovery), the Workbench foundation, and the Compatibility View that embeds the official DeepSeek Harness Web UI. Today the content area is still primarily the Compatibility View — the same server `pnpm dsh web` starts, reused verbatim — but the official Web UI is the current compatibility surface and regression baseline, not the product ceiling. Harness remains the only runtime; DeepCode adds no second session, credential, or configuration store.

## First run (for non-programmers)

1. Run the installer (`DeepCode-Setup-…exe`); no administrator rights are needed.
2. Double-click **DeepCode** (desktop or Start menu shortcut).
3. Open **Settings** from the bottom-left, then the **Models** page.
4. Paste your DeepSeek API key. The key is stored by the DSH credential mechanism in the application's own data folder — never in the installer, logs, or command line.
5. Go back to the home page and choose a workspace folder.
6. Start a new session and talk to the agent.

The packaged app keeps its data in `%APPDATA%\DeepCode\dsh` (credentials, settings, sessions, profiles) and never reads a global `~/.dsh`. Uninstalling the app **keeps** your data in that folder — close the app first, then delete the folder manually to clear everything. The standard Chromium `--user-data-dir=<path>` switch relocates the entire Electron userData (launcher state, single-instance lock, Managed Home, diagnostics log) for portable use and test isolation; on Windows userData resolves through the Known Folder API and never follows the `APPDATA` environment variable.

## Run from source

From a repository checkout (Node.js and pnpm required):

```sh
pnpm install
pnpm run build        # builds the Web UI dist the shell serves
pnpm run dev:desktop  # opens the DeepCode window
```

`dev:desktop` compiles `apps/desktop` and launches Electron. The main process starts the local DSH Web service on the fixed loopback port `3080`, waits until the server responds, and only then creates the window. Closing the window hides it and Harness keeps running from the system tray; Quit DeepCode (tray or menu) stops the DSH service and exits — no background Node process or port is left behind after a real quit.

## Build a portable distribution and installer (Windows)

One command produces a self-contained, double-clickable Windows folder plus a per-user NSIS installer:

```sh
pnpm run build:desktop-dist   # rebuilds lib/web/desktop from current source, then packs, installs, assembles, sanitizes, packages
```

The command always rebuilds its inputs (`build:lib:host`, `build:web`, `build:desktop`) from the checkout as it is now, so the distribution can never package stale artifacts; the committed app icon is regenerated only if missing.

The results are `dist/desktop/win-unpacked/DeepCode.exe` and `dist/desktop/DeepCode-Setup-<version>.exe`. The folder embeds the full DSH runtime (`resources/dsh/node_modules`), the Web UI dist, and the shell; it needs no Node.js, pnpm, or the source checkout. The exe acts as its own Node runtime (`ELECTRON_RUN_AS_NODE`), so no PATH entry is consulted. The installer installs for the current user only (no admin rights), with Start menu and desktop shortcuts. The build sanitizes the payload before packaging and fails loud if the output leaks `.git`, `.env`, session logs, user paths, or API keys. Version gates make a mismatched delivery impossible: the declared dsh tarball version must equal the version actually installed into the runtime, the installer filename must carry the DeepCode app version, and the build writes `resources/dsh/source-commit.txt` (git HEAD) so every distribution is traceable.

## How it works

| Concern | Mechanism |
|---|---|
| DSH service | spawns the `@deepseek-ai/dsh` entry — `node --import tsx/esm apps/cli/src/bin.ts` in the repository root (dev) or the packaged exe with `ELECTRON_RUN_AS_NODE` running `resources/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js` (packaged) — always with `--host 127.0.0.1 --port 3080`. `--profile` and `DSH_HOME` come solely from the launcher state's active selection through `resolveDshLaunch` in `src/dsh-service.ts`. |
| Launcher state | `%APPDATA%\DeepCode\launcher-state.json` (under Electron userData, never inside `DSH_HOME`) records the active harness selection: a home reference — `managed`, which resolves to `%APPDATA%\DeepCode\dsh` at runtime, or `existing`, an explicit absolute path used as-is (spaces and Unicode preserved, never created, migrated, or merged) — plus a profile name (default `web`; any name the official profile rules accept — non-empty, no `/` or `\`, not `.`/`..`/`node_modules` — is valid, and Web-capability discovery belongs to a later package). The record is `schemaVersion: 1` with `active`, `pending`, `lastKnownGood`, and `lastBootFailure` — a length-capped, credential-redacted record of the most recent failed switch/restart; an ordinary start leaves it intact, and only the next fully successful switch or restart clears it. A missing file means the default (managed + web). A corrupted file opens an in-app rescue instead of a dead end: restore defaults (the broken file is first copied verbatim to `.invalid-<timestamp>`, then the default is written atomically — user homes, sessions, credentials, profiles, and plugins are never touched), open the containing folder, or quit. Writes replace the file atomically (temp file in the same directory + rename). |
| UI state | `%APPDATA%\DeepCode\desktop-ui-state.json` (under Electron userData, separate from launcher state) holds exactly five preference facts: `windowBounds`, `maximized`, `themePreference` (`system`/`light`/`dark`, default `system`), the acknowledged recovery-notice hash, and the Expert Details panel expansion. The strict parser rejects every unknown field — session, model, credential, Profile, selection, plugin, Memory, Compaction, and Hook facts are impossible to store — and writes are atomic. Reads never throw: a corrupted UI state degrades to safe defaults with a logged reason, so a UI preference can never block the launcher or the Harness runtime. |
| Data home | dev and packaged share one rule: the active selection decides `DSH_HOME`. The `DSH_HOME` environment variable does not override the selection. |
| Port conflict | a TCP probe runs before spawning; an occupied port shows an understandable error dialog and exits with code 1 — no silent port switch, no retry. |
| Readiness | polls `http://127.0.0.1:3080/` until an HTTP response arrives (60s cap), then opens the window. |
| Window | `BrowserWindow` with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`; the renderer has no Node, shell, or file access. In-window navigation is restricted to the local DSH origin and new windows are denied; external `http`/`https` links open in the system default browser, and no remote page ever loads inside the window. The window title stays `DeepCode`. Position, size (min 800×520), and maximized state are saved at event boundaries (debounced, no polling) and restored clamped to the current display's visible work area, so monitor pulls, DPI, and resolution changes never leave the window off-screen; a minimized window never overwrites the saved bounds. The window uses one plain themed background path only — material surfaces (Electron `backgroundMaterial`/transparency) make Chromium drop ClearType subpixel antialiasing and visibly degrade the official page's text, so they stay removed until re-proven on a high-DPI machine. |
| Single instance | a second launch exits immediately and brings the existing window to the front. |
| Diagnostics | the packaged app writes DSH service output to `%APPDATA%\DeepCode\dsh-service.log` through a bounded rotation policy (current + up to 4 history files = 5 total, plus a total-size budget, oldest deleted first — crash evidence shifts into history on the next ordinary start instead of being clobbered). Credential-shaped text — API keys, GitHub/Slack tokens, AWS access-key ids, Bearer tokens — is redacted by one shared rule set, streaming-safe even when a secret is split across stream chunks; error dialogs point there. Dev and smoke inherit the console. |
| Shutdown | Quit DeepCode (tray or chrome menu) is the only real exit: an honest confirmation, then `controller.stop()` terminates the whole DSH process tree and its exit is awaited, the tray and views are destroyed, and the app quits. The window X hides the window (resident tray mode; a one-time balloon explains it). OS shutdown/logoff takes the non-interactive orderly cleanup path. An unexpected DSH crash keeps the chrome and tray alive: the controller becomes the single failed-status source (stage `runtime`), the UI shows the redacted diagnosis, and Restart Harness boots the active selection — no auto-restart loop. |
| Tray | a resident `Tray` whose menu is rebuilt from the same control model as the chrome (one selection, one runtime status): Open DeepCode, read-only active Profile, live Harness status, Profiles quick-switch submenu (radio, startable profiles only), Restart Harness, Open Harness Panel, Open DSH Terminal, Check for Updates (shows the new version when one is available), About, Quit DeepCode. |
| DSH Terminal | a terminal window rendering a real ConPTY (pty host = `ELECTRON_RUN_AS_NODE` + runtime `node-pty`; xterm UI). The host selection probes exact paths in order — Windows Terminal (`wt.exe`) → PowerShell 7 (`Program Files\PowerShell\7\pwsh.exe` or the Store alias; a user-terminal recommendation only) → PowerShell (System32) → cmd (System32); Windows Terminal opens as its own window, otherwise the chosen shell runs embedded. Without PowerShell 7 the Harness panel shows one non-blocking recommendation line (`winget install --id Microsoft.PowerShell --source winget`) — never a popup loop, never an automatic install; the Agent's sandboxed PowerShell always runs through Harness' tool/security path, so detecting pwsh never bypasses the sandbox. cwd prefers the active Profile directory (falls back to Harness Home with a welcome note). The PATH carries runtime-generated private shims (`userData/deepcode-bin/`: `dsh`/`node`/`pnpm` forwarding to the current exact executable, the shim dir never touching the system PATH/registry/shell configs), and bare `dsh`/plugin commands default to the active Profile via an argv-level wrapper (`--profile X` always wins; `-h`/`--version` pass through). The welcome line shows DeepCode/DSH versions, the active Profile, DSH_HOME, and the private-runtime source of Node/pnpm/dsh. The host runs through the Desktop Command Broker — exact executable + argv, never a shell string, never `shell: true`, streamed output with credential redaction, cancel kills the whole tree, one maintenance operation at a time. Closing the terminal window cancels the host; a launch failure is reported explicitly, never an infinite fallback. |
| Plugin Manager | a Harness-panel second-level page (Desktop Chrome only, never injected into the Compatibility View) managing profile plugins through the official `dsh plugin --profile <target> <pnpm args...>` path — no marketplace, recommendations, remote catalog, or "popular" lists. The inventory shows three never-mixed fact classes from single sources: Profile Bundles (the `dsh profiles --json` `bundles` layers; template bundles vs. dependency-derived ones are distinguished by crossing the manifest `dependencies` keys), Installed Dependencies (the profile `package.json` `dependencies`, read-only), and Effective/Loader facts (the official `staticStatus`/`evidence`). A dependency existing in package.json never implies it loaded. Every write (add/remove/update/install) is preceded by a target-transparency confirmation (Home kind, full path, Profile, operation, spec; an Existing Home shows "这次操作会修改你选择的现有 Harness Profile。"), runs through the Desktop Command Broker's maintenance slot (independent from the resident terminal's slot — a plugin operation never blocks the terminal or vice versa), streams redacted output with cancel (whole tree), does the post-check only after exit 0 (re-reads discovery + manifest from disk and verifies the expected change), then refreshes the inventory and offers a Restart Now / Later handoff ("插件变更已完成，需要重启 Harness 才会进入新的 Loader composition。") — never auto-restarting. Discovery, browsing, and refresh are zero-write; only explicitly confirmed management actions write the target profile. Local path specs are anchored to a user-chosen directory and pre-checked for existence (pnpm silently links missing directories with exit 0, so the desktop rejects them first); every spec is a single argv element, and both the typed spec and the anchored result are rejected when they contain whitespace, cmd metacharacters or control characters — the official CLI forwards pnpm through a Windows shell, so the desktop boundary is what keeps a spec or an anchor directory name from becoming a command. A "How to install a plugin" help block states plainly that DeepCode runs no marketplace and where compatible plugins come from. Every confirmed GUI write enters a protected transaction: before running, DeepCode snapshots the three whitelist files (`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`; absent is recorded as absent, never faked) byte-identically plus hashes, and keeps a recovery journal only inside its own userData — the write path itself stays the official CLI. After a successful post-check the journal becomes pending-verification, and the change is only considered verified once the next Harness generation actually comes up healthy (HTTP readiness + official UI mounted + the DeepCode client theme plugin settled — never just "port answered"). One pending unverified transaction per Home/Profile is enforced; Restart Later keeps the journal for the next launch to verify. If the next generation fails, the journal's post-hashes are checked first: any external drift (a whitelist file changed after the operation) stops recovery cold and offers only manual entries (Open Profile Folder / Open DSH Terminal / Abandon — never an overwrite). Without drift, a Managed Home restores the three whitelist files from the snapshot and restarts automatically at most once (a second failure stops the automation); an Existing Home never restores without an explicit confirmation listing the exact files. `node_modules` is never backed up or restored; there is no transaction database — one narrow journal plus three file snapshots, nothing more. |
| Update service | compares DeepCode app versions only — never the embedded DSH version. The provider reads an HTTPS feed manifest (strictly parsed: stable `latestVersion`, release notes, assets with HTTPS URL + SHA-256 + size + safe filename); the feed config lives in `userData/deepcode-update-feed.json`, and while the repo is private there is no public channel — Manual Check says "当前未配置公开更新通道", the background check ends silently, no personal token is ever requested and no repo credential is ever packaged. The background check (delayed, non-blocking) is silent on network errors and only surfaces a strictly newer stable version (one tray balloon per version). Manual Check reports current/failure/unconfigured explicitly; downloads require explicit confirmation, cancel stops the stream, partials are cleaned, the size cap and SHA-256 digest are verified before anything can run, and only the configured HTTPS URL is ever fetched. After verification, an explicit "退出 DeepCode 并开始安装更新？" handoff stops Harness, closes views/tray, spawns the verified NSIS installer (exact path, detached), and exits; a spawn failure keeps the current app usable and never deletes the current installation. Verified installers use a single-slot retention policy: the update cache holds at most one artefact (a new download clears the directory first), and a verified installer recorded on disk is restored after a restart and re-verified against its recorded digest immediately before the handoff, so a wrong or tampered file is refused rather than run. SmartScreen limitation is stated in the UI and docs (no code-signing certificate yet; no fake signature verification). |
| Diagnostics Center | a chrome panel (menu: 诊断中心) showing allowlisted facts only — DeepCode version, embedded DSH version/source, Electron/platform/arch, active Home kind (never a path), active Profile, Harness status, diagnostics log location, and update channel — plus three actions: Open Log Folder, Copy Build Info (main-process clipboard), and Export Diagnostics Bundle. The bundle is a local directory under `userData/diagnostics/` (never uploaded): a `bundle-manifest.json` listing every included file with source and size, redacted log copies (current + all rotated history), a last-exit fact (an `active-run.json` marker is written on start and removed on orderly quit, so a leftover marker is the minimal "previous run did not end normally" evidence — never an automatic crash claim), local Crashpad dumps (collected with a 50 MB total budget, newest first, anything skipped is recorded in the manifest instead of being faked as exported), and a build-info text; credentials, `.env`, and session content are structurally excluded (filename allowlist, no session logs), and user paths are normalized to `<USER_HOME>` before export. Crash dumps may contain local paths and memory fragments, so the export dialog says to review the bundle before sharing it publicly. Export failure never deletes original logs or user data. When the GUI cannot start at all, `DeepCode.exe --export-diagnostics` runs headless: it starts no Harness, no profile, no third-party plugin, no window, no tray, and never listens on 3080 — it only assembles and exports the same local bundle, prints the bundle path to stdout, and exits (60s cap, non-zero exit on failure). |
| Permissions | Harness is the single permission truth; DeepCode stores no permission state of its own. The Harness panel shows the real permission mode read live from the official settings service — `Permissions: Sandbox` (the recommended default, `workspace-write` sandbox + ask-approval), `Permissions: Full Access` (`danger-full-access`), `Read-only`, or `Custom`. A fresh Managed Home starts with the recommended Sandbox preset; if the official service has no explicit default yet, DeepCode writes the recommended preset through the official settings API before the first agent session — an Existing Home is only ever displayed, never silently changed. Switching to Full Access always requires an explicit risk confirmation ("Full Access allows Agent tools to act with the permissions of your Windows account. Files outside the current workspace may be readable, writable, or deletable. Use this only when you understand the risk."); switching an Existing Home to Sandbox also confirms first ("这会修改你选择的现有 Harness 设置。"). When the permission service cannot be read, the UI fails closed: it shows `Permission controls unavailable` and never pretends to be Sandbox or silently falls back to Full Access. Agent approvals stay native Harness behavior — DeepCode never auto-approves, never swallows the approve/deny UI, and keeps no trust cache of its own. |
| Log retention | the service log rotates at open time through a bounded policy (current + up to 4 history files = 5 total, plus a total-size budget, oldest deleted first) instead of the old current + `.old` pair — crash evidence is shifted into history by the next ordinary start, never immediately clobbered, and logs can never grow unboundedly. Every file is written through the same streaming credential redaction. No log database, no background cleanup service. |
| Release integrity | the distribution build writes a `SHA256SUMS.txt` release manifest (installer + unpacked exe), and `verify-desktop-dist.ps1` additionally gates: app.asar present (Desktop Chrome assets shipped), the four license notices (PolyForm / DEEPCODE-LICENSE / MIT / THIRD_PARTY_NOTICES), no session logs (`.jsonl`) anywhere in the payload, and every manifest digest re-computed and matched. |
| Desktop Chrome | DeepCode owns the 47px top bar (hidden system title bar, native Windows window buttons via `titleBarOverlay`): an always-visible hamburger menu, a quiet centered page title (hidden below ~900px width), and a clickable Harness status pill mapping the controller's seven runtime phases to colors (grey idle/stopping, blue starting/switching, yellow recovering/recovered, green running, red failed), updating live during switches. The hamburger menu and the pill open the same Harness panel: Home kind, path (compact by default — last two segments — with the full value on hover, never spread across the top bar), active profile, runtime status, per-profile switch (verified profiles direct, unverified ones "尚未验证，可以尝试启动", no-interface/misconfigured ones disabled with a plain reason, previously failed ones marked "上次启动失败"), Refresh, Choose Existing Home (directory picker → read-only discovery → in-panel profile choice → controller.switchTo; every cancel writes nothing), Use Managed Home (web), Restart, Expert Details (collapsed by default: full path with Copy Full Path — copied via the main-process clipboard, never sent to network or logs — pending switch, and the failed target with its stage; technical facts stay reachable, never deleted), and inline Recovery Details (redacted failure, recovery target, log path). The hamburger menu also carries Theme (System/Light/Dark, default System, following `nativeTheme`; the chrome themes only itself — the official Web UI in the Compatibility View is never injected) and About DeepCode (a dialog assembled from controlled facts only: app version, embedded DSH version/source, Electron, platform/arch, Active Home kind, Active Profile, license summary, repository — no API keys, credentials, session content, or environment variables can appear). After a real recovery (a failed configuration booted, and the controller fell back to last-known-good), a non-blocking top-bar banner says "刚才的配置没有启动成功，DeepCode 已恢复到 <profile>。" with View details / Got it — shown once per failure fact, acknowledged in UI state, never clearing the persisted failure and never fabricating a recovery. The chrome is a trusted local renderer behind a narrow preload API with a closed command union validated in main; Chinese text serves zh locales with English as the fallback. |
| Delivery identity | the About dialog and every artifact carry four facts from single sources: the DeepCode app version (`apps/desktop/package.json`, `1.0.0` for the first public release, independent of the DSH repository version), the embedded DSH version read from the actual packaged runtime, the embedded DSH source/commit identifier, and the Electron version + platform/arch — assembled by `src/version-info.ts`, each with exactly one authoritative source and a build gate that fails loud on disagreement. |

## Smoke mode

`DSH_DESKTOP_SMOKE=1 pnpm run dev:desktop` runs the same startup path without GUI dialogs: it prints `[deepcode] window loaded` once the page finishes loading, closes the window, and exits — useful for scripted verification without a model conversation.

## Upstream compatibility suite

`pnpm run test:desktop-parity` drives the packaged `dist/desktop/win-unpacked/DeepCode.exe` through playwright-core's Electron driver in a fully isolated environment (Electron userData relocated into the test temp root via `--user-data-dir`; `APPDATA`/`LOCALAPPDATA`/`DSH_HOME` pinned there as defense in depth; credential-shaped environment variables stripped; no model calls). A missing packaged exe fails the run. The suite guards upstream Web/Harness capabilities against regression — 4 lifecycle rows verified, 25 functionality rows tracked as compatibility backlog. Planned work is never recorded as verified.

## Packaged acceptance (B1 Case A–F)

`pnpm run test:desktop-parity` also drives the B1 packaged acceptance: Case A fresh Managed/web; Case B an Existing Home with two compatible profiles, switched and restarted through the Desktop Chrome status pill and Harness panel (real DOM clicks on the production control entry, not a test helper); Case C a profile-local third-party Cordis plugin executing for real inside the packaged exe; Case D an apply-throw switch falling back to last-known-good; Case E the selection surviving close and relaunch; Case F profile definitions, the third-party package, and sentinels never copied, migrated, or rewritten, with discovery-only runs provably zero-write and Existing sentinels never appearing in the Managed Home. Every case runs in an isolated temp root containing spaces and Unicode, strips credential-shaped environment variables, makes no model calls, and verifies the packaged exe needs no external Node, pnpm, or PATH entry.

## Installing the unsigned build

The first release is not code-signed — the audience is developers, comparable clients ship unsigned, and at this stage the money belongs in the product — so Windows SmartScreen stops the installer and reports an unknown publisher. That is not a signal about the file's safety, only that no certificate was bought for it — but precisely because there is no signature to lean on, verify the hash yourself before installing.

**To continue**: in the SmartScreen dialog, choose "More info" then "Run anyway".

**To verify the download** (the stand-in for a signature; expected values ship next to the installer in `SHA256SUMS.txt`):

```powershell
Get-FileHash .\DeepCode-Setup-<version>.exe -Algorithm SHA256
```

Install only if the printed `Hash` matches the corresponding line in `SHA256SUMS.txt` exactly. If it does not match, do not run it — please open an issue instead.

## Known limitations

- No code signing (Windows SmartScreen will warn about the unknown publisher; see the section above for how to continue and how to verify the download), auto-start, or account system; the update service is present but ships unconfigured — while the repository is private there is no public update channel, so Check for Updates shows "当前未配置公开更新通道" until an HTTPS feed manifest is published and configured (`userData/deepcode-update-feed.json`).
- Tested on Windows x64 only; macOS and Linux are not exercised.
- A forcibly killed Electron process (task manager) can leave the DSH child running; the window-close and quit paths always clean up.
- The distribution is large (~540MB unpacked, ~145MB installer): Electron plus the full DSH web-profile runtime closure.
- Plugin Manager v1 scopes: targets are limited to already-discovered profiles under the active Home (no auto-init of new profiles, no cross-Home writes, no marketplace); install/repair is the official `pnpm install` forward (pnpm has no separate `repair`); specs containing whitespace are rejected (the official CLI forwards pnpm through a Windows shell and splits space-containing path arguments — the desktop refuses at the boundary instead of working around the CLI), and a DSH_HOME path containing spaces has the same upstream constraint for local-path adds; local path adds support spaces only via moving the directory to a space-free path first. The same upstream forward makes caret ranges (`^1.0.0`) and compound semver ranges containing `|`, `>` or spaces unsupported (cmd would eat the caret and silently narrow the range), and a local plugin path — including the anchor directory chosen in the picker — must be free of whitespace and cmd metacharacters.

## Resident host (tray) and DSH Terminal

DeepCode runs resident: clicking the window X hides the window and Harness keeps running from the system tray (a one-time non-blocking balloon explains this on first close; the acknowledgement lives in the UI state). The tray menu is rebuilt from the same control model as the chrome — Open DeepCode, the read-only active Profile, the live Harness status, a Profiles quick-switch submenu, Restart Harness, Open Harness Panel, Open DSH Terminal, Check for Updates, About, and Quit DeepCode. Quit confirms with the honest prompt "退出 DeepCode 会停止 Harness，并中断当前正在执行的任务（如果有）。" (it never claims to have detected a running task), then stops the full DSH process tree, destroys the tray and views, and exits. Running the shortcut again shows and focuses the existing window — never a second Harness. OS shutdown/logoff takes the non-interactive orderly cleanup path (no blocking dialogs). If the DSH child exits unexpectedly, the chrome and tray stay alive, the controller becomes the single failed-status source (stage `runtime`), the UI shows the redacted diagnosis, and Restart Harness boots the active selection — no auto-restart loop, no fallback loop.

Open DSH Terminal opens a terminal chosen by probing exact paths — Windows Terminal → PowerShell 7 (user-terminal recommendation only) → PowerShell → cmd — through the same service from the tray and the chrome. The terminal's DSH_HOME is the launcher active Home's real path, its cwd prefers the active Profile directory (Harness Home fallback is explained in the welcome), and bare `dsh`/plugin commands default to the active Profile (`--profile X` always wins). The terminal PATH prepends runtime-generated private shims (`userData/deepcode-bin/`) that forward to the current exact executable; the shim dir never touches the parent environment or any permanent environment variable, downloads nothing, and guesses no system installation. The welcome shows the DeepCode/DSH versions, active Profile, DSH_HOME, and the private-runtime source of Node/pnpm/dsh. The packaged distribution pins a private pnpm runtime (`resources/dsh/node_modules/pnpm`, locked by `runtime.package-lock.json`) executed through the DeepCode.exe itself — system Node/pnpm, the global PATH, the registry, PowerShell profiles, and shell configs are never read or modified, and the packaged verification asserts all three (Node, pnpm, DSH CLI) really execute.
