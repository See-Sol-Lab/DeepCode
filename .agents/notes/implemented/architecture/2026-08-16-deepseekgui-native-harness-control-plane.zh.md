# Agent Note: DeepSeekGUI harness home and launcher selection core

Status: implemented

[English](2026-08-16-deepseekgui-native-harness-control-plane.md) | 中文

## Problem

桌面壳此前没有持久化的"用哪个 Harness Home、哪个 profile 启动"概念：`--profile web` 硬编码在 `resolveDshLaunch` 里，打包版把 `DSH_HOME` 固定为 `userData/dsh`（环境变量可覆盖），开发态继承宿主环境。后续控制面——启动选择 UI、pending/last-known-good 恢复语义、更多 profile——需要一份持久化的选择作为唯一真相来源，并且 schema 要大声失败而不是静默改写用户状态。

## Decision

`apps/desktop/src/launcher-state.ts` 定义 launcher 状态及其存取器。`HarnessHomeRef` 是闭合联合：`managed`（运行时解析为 `join(userData, 'dsh')`，不触碰全局 `~/.dsh`）或 `existing`（只接受显式绝对路径，原样保留空格与 Unicode，绝不创建、迁移、合并）。`HarnessSelection` 由 home 引用加 profile 名称组成；`LauncherStateV1` 为 `schemaVersion: 1` 加 `active`、`pending`、`lastKnownGood` 与 `lastBootFailure`（固定 `null`，后续包扩展为 `BootFailure | null` 时无需新增或迁移字段）。profile 是普通字符串，按与 `@deepseek-ai/dsh-app-boot` 的 `resolveProfileDir` 完全一致的命名规则校验：非空、不含 `/` 或 `\`、不得为 `.`、`..`、`node_modules`。`headless`、`tui`、自定义名称与 spaces/Unicode 名称在 schema 层均合法；是否 Web-capable 留给后续 discovery/control 判断，绝不在此决定。默认仍为 managed + `web`。

状态只存在于 Electron userData 下的 `launcher-state.json`，绝不写入 `DSH_HOME`。`LauncherStateStore.read()` 在文件缺失时返回默认状态（managed + web，pending/last-known-good/last-boot-failure 为空）——新用户路径——且不创建文件；无效 JSON、未知 `schemaVersion`、未知字段或非法字段值（非法 profile 名称、非绝对路径的 `existing.path`、非 null 的 `lastBootFailure`、任意层级的多余键）抛 `LauncherStateError`，消息带字段路径，绝不回退或覆盖。`write()` 经 JSON 往返复用同一严格解析器校验状态，按稳定键序序列化（2 空格缩进、结尾换行），用同目录临时文件 + `rename` 原子替换，失败时清理临时文件。

`dsh-service.ts` 的 `resolveDshLaunch` 不再硬编码 `--profile web`，也不再接收仅打包态使用的 `packagedDshHome`：改为必填的显式 `profile` 与 `dshHome`。开发态与打包态共用同一入口——`@deepseek-ai/dsh` 的 bin（开发态经 tsx 跑 `apps/cli/src/bin.ts`，打包态由 `ELECTRON_RUN_AS_NODE` 跑 `resources/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js`）——与同一固定 `--host 127.0.0.1 --port 3080`。两种形态都从 selection 注入 `DSH_HOME`；`DSH_HOME` 环境变量不再覆盖。`main.ts` 启动时读取 store，用 `state.active` 启动，状态文件无效时以可理解的对话框报错退出。单实例锁、仅回环监听、日志脱敏与 Windows 进程树清理保持不变。

Profile inspection 以 boot-free、只读的形式发布。`@deepseek-ai/dsh-app-boot` 导出 `inspectExistingProfile`、`inspectExistingProfiles` 与 `classifySurface`：这些 helper 复用官方 manifest 读取、双锚点 bundle 解析、patch 解析（`loadOptionalPatches`/`loadOverlayPatches`）与空根组合语义，并按真实启动的层序组合完整静态 composition——各组合包 patch、profile 自身的 `cordis.patch.yml`、home 级 `$DSH_HOME/cordis.patch.yml`（缺失视为空层，绝不创建）——绝不调用 `initProfile`、`normalizeShippedProfile`、`healProfilesModuleFallback` 或 `writeProfileManifest`，绝不生成或重写 `cordis.yml`。`dsh profiles --json` 打印一份文档——`schemaVersion: 1`、解析出的 `DSH_HOME`，以及每个 profile 的 `name`/`dir`/`bundles`/`staticStatus`/`evidence`（malformed 时为 `error`）——stdout 只承载 JSON，诊断走 stderr；home 或 `profiles` 目录缺失时返回空列表且不创建任何东西。静态状态：仅当官方 `web-startup`/`webserver`/`web-runtime` 行携带官方插件名（`@deepseek-ai/dsh-web-app/startup`、`@deepseek-ai/dsh-host-webserver`、`@deepseek-ai/dsh-web-app`）且无字面 `disabled: true` 时才为 `web-capable`；`headless` 是对 `headless-startup`/`headless-runner`（`@deepseek-ai/dsh-headless/startup`、`@deepseek-ai/dsh-headless`）的同款检查；`malformed` 表示该 profile 的检查抛出错误；其余都是 `candidate`。字面 `disabled: true` 算关闭，非字面动态 `disabled`、官方 id 下的自定义插件名与自定义 surface 绝不猜测，boot-failing 留给真实启动。单个损坏 profile——或每个 profile 都会读取的损坏 home patch 层——只产生逐 profile 的 `malformed` 条目，绝不拖垮整个 home。每条失败消息在进入 JSON `error`、CLI stderr 或桌面端之前都会做凭据脱敏：API key（`sk-…`）、GitHub token（`gh*_…`）、Slack token（`xox*…`）、AWS access-key id（`AKIA…`）与 Bearer token 各自保留前缀并以 `<redacted>` 结尾。桌面端 `apps/desktop/src/profile-discovery.ts` 用与 launcher 启动完全相同的 DSH 入口/环境构造（`resolveDshCommand`）运行 `profiles --json`，并严格校验文档（未知 schema 或字段一律拒绝；`malformed` 必须携带非空 `error`，非 `malformed` 不得携带）——不引入 YAML 依赖、没有第二 parser；子进程 stdout/stderr 以 UTF-8 流式收集（`setEncoding`），被管道分块从中间切开的多字节字符也能正确重组。

Restart boundary 与 last-known-good recovery 位于 `apps/desktop/src/harness-controller.ts`。`HarnessController` 拥有 launcher state 上的切换协议与内存 runtime 状态，共七相——`idle`、`starting`（初次启动或 restart 的 boot）、`switching`（新 selection 的 boot）、`recovering`（last-known-good 回退 boot）、`stopping`（stop 被请求的瞬间同步进入）、`running`、`failed`——只协调 launcher state、selection 解析、spawn/HTTP 就绪/页面加载与停止，不拥有 Harness 的 settings、sessions、credentials 或 plugins。`switchTo(selection)` 先原子持久化 `pending`（active 与 last-known-good 原样保留），完整停止当前进程树，再启动 pending 的 selection；只有 spawn、HTTP 就绪、`loadURL` 全部成功，才把 pending 同时晋升为 active 与 last-known-good 并清空 pending。失败时停掉失败进程、记录限长脱敏的 `lastBootFailure`（`stage` ∈ `spawn`/`readiness`/`page-load`；空错误消息回退为带阶段的默认文案，schema 拒绝超过 512 字符的消息）、清空 pending，并只尝试一次 last-known-good——成功表现为 `recovered: true` 且**保留**持久化的失败记录作为本次切换的证据（只有下一次完整成功的 switchTo/restart 才清除；普通启动成功不动它），失败让内存状态停在 `failed`，绝不循环。启动时读到遗留 pending 视为 interrupted switch：清空它（绝不自动继续），并启动 last-known-good ?? active。凡是经同一三关门槛完全成功的启动——`start()`（active 或回退的 LKG）、切换晋升、`restart()`——都会把本次启动的 selection 落为 last-known-good：从未切换过的用户第一次切到坏 profile 时也有回退目标。`restart()` 只重启 active——不创建 pending、不改 Home/Profile、失败不做 recovery——它成功与下一次成功的切换晋升是清除旧 `lastBootFailure` 的唯二时机。`stop()` 同步标记 shutdown 并立即进入 `stopping`，立刻终止子进程，让在途的 readiness 等待、页面加载或 fallback 尽快结束：用户关窗不记新 failure、不 fallback、不晋升、绝不继续 boot；已写入的 `pending` 留在磁盘上，交给下次启动的 interrupted-switch 规则（退出路径绝不伪造一次成功或失败）；进程树恰好清理一次，最终状态为 `idle`。`LauncherStateV1.lastBootFailure` 从 P1 固定 `null` 放宽为 `BootFailure | null`，`schemaVersion` 仍为 1（无需新增或迁移字段）；`BootFailure` 另带可选的 `selection` 字段，记录启动失败的 selection（旧状态文件仍可解析）。所有公共操作经同一队列串行化：并发调用按到达顺序执行、重复 stop 共享同一个进行中的清理；主进程的 runtime adapter 保持一次 stop 后可安全 restart 的生命周期，固定回环、端口探测、日志脱敏、Windows `taskkill /T /F` 与打包态无 Node/pnpm 路径不变，并对每个新 spawn 的子进程挂 unexpected-exit 监视（boot 进行中与主动停止不误报），switchTo/restart 之后的子进程绝不无人监视。

面板，两处入口复用同一模型与同一动作路径。数据单向流动：launcher-state + `HarnessController`（新增 `onStatusChanged` 回调把每次 `setStatus` 转移收口上报）+ 只读 discovery → main 构建可序列化 `DesktopControlModel`（`control-model.ts`）→ 窄 第三方 Cordis 插件支持由 keyless e2e 证明，而非生产实现。`apps/desktop/tests/fixtures/native-proof-plugin` 是一个最小第三方风格 Cordis 函数插件（包名 `deepseekgui-native-proof-plugin`，不是 workspace 包）：生产代码从不 import 它，打包 runtime 绝不把它当内置——它只因测试构建的 profile 列出它才挂载。其唯一可观察效果来自 `apply(ctx, config)`：写一个 JSON marker（nonce、插件名、pid、ppid、`DSH_HOME`），并可按配置故意抛错或提供回环就绪门。`apps/desktop/tests/native-plugin-proof.e2e.ts` 搭建真实 Existing `DSH_HOME`（profiles manifest + `cordis.patch.yml` insert row + profile-local `node_modules/deepseekgui-native-proof-plugin`，复制就位、不跑 `pnpm install`），然后证明：boot-free discovery 不产生 marker；经 launcher 自身向量（`resolveDshCommand` → 官方 dsh boot → profile composition）启动后 fixture 挂载，marker 的 pid 等于实际 DSH child pid、其 `DSH_HOME` 等于 Existing Home、nonce 与经插件行 config 传入的值匹配；删掉 insert row 不产生 marker；故意 apply-throw 使 pending 启动失败，controller 单次回退 last-known-good（`recovered: true`、`lastBootFailure.stage: 'readiness'`、selection 指向失败的 profile）；profile manifest、patch 与 fixture 文件在 discovery 与各次 boot 前后字节不变。不调用模型、不要求 API key。fixture 是测试数据准备，不是生产复制逻辑：DeepSeekGUI 不理解 marker、也绝不代写它。

B1 以打包 Windows 验收收口（`apps/desktop/tests-e2e/packaged-acceptance.e2e.ts`，由 `test:desktop-parity` 运行），在含空格与 Unicode 的隔离临时根内直接驱动 `dist/desktop/win-unpacked/DeepSeekGUI.exe`。Case A 证明全新安装以 Managed/web 启动并落默认状态（active == lastKnownGood == managed/web，pending 与 lastBootFailure 为 null）；Case B 经 production control entry——Desktop Chrome 上的真实 DOM 点击（状态胶囊 → Harness 面板 → 稳定元素 id `harness-switch-profile` / `harness-profile-<name>` / `harness-restart`），由 Electron main-process evaluate 在 chrome view 的 webContents 内执行——在 Existing Home 的两个 web-capable profile 间切换与重启；Case C 在打包 exe 内复现 P5 插件证明（marker ppid 等于 Electron 主进程 pid、marker pid 与之不同——即 `ELECTRON_RUN_AS_NODE` 的 DSH 子进程）；Case D 证明 apply-throw 切换回退 last-known-good 且失败持久化（`stage: 'readiness'`、selection 指向损坏 profile、Harness 面板的内联恢复详情出现）；Case E 证明 selection 跨关闭重开保持；Case F 证明 DeepSeekGUI 绝不复制、迁移或改写 profile 定义、第三方包或 sentinel——真实 boot 中官方 Harness 仍可维护自己的 `cordis.yml` 与 `profiles/node_modules` fallback——且 discovery-only 运行前后字节与目录树完全一致、Existing sentinel 绝不进入 Managed Home。打包 exe 还以仅含 `C:\Windows\System32` 的 PATH 启动成功（无外部 Node/pnpm），关闭后释放 3080 端口且无残留进程。全程不调用模型、不要求 API key。

## Alternatives considered

- **引入 JSON schema 库（zod 等）**：拒绝——桌面包不带任何运行时依赖；手写严格校验约百行，且每条失败消息都带字段路径、可控中文。
- **文件无效时回退默认值**：拒绝——把损坏文件当"首次运行"会静默丢弃用户既有选择，之后的覆盖写入会彻底毁掉它。大声失败、让用户修复或删除文件才能保住数据。
- **保留 `DSH_HOME` 环境变量覆盖**：拒绝——一个启动事实不允许两个真相来源。selection 是唯一来源；测试隔离继续成立，因为 parity 环境重定向的是 `APPDATA` 本身。
- **状态 schema 用 `['web']` 白名单**：拒绝——状态记录的是启动选择，不是启动能力；Web-capable 的发现是后续包的职责，若用白名单，任何自定义 profile 名都要先改 schema 才能持久化。schema 只做官方 profile 命名规则校验。
- **在 Electron 里重做 discovery**（桌面侧 profile parser 或 YAML 依赖）：拒绝——桌面端用与启动完全相同的入口与环境构造运行官方 CLI 的 `profiles --json`，分类因此复用 harness 自身的 manifest、bundle 与 patch 语义，而不是桌面侧复制一份；两者不一致时会表现为 schema 失败，而不是静默误分类。

## Consequences

- 新用户默认启动不变（managed + web）；开发态现在经同一 selection 路径解析 `DSH_HOME`，不再继承宿主环境。
- v1 记录已携带 `lastBootFailure: null`，后续包把字段类型放宽为 `BootFailure | null` 时无需新增或迁移字段；严格解析器当前拒绝一切非 null 值。
- parity 与打包验收 e2e 经 Chromium 标准开关 `--user-data-dir` 隔离 Electron userData（Windows 上 userData 走 Known Folder API、忽略 `APPDATA`）；`APPDATA`/`LOCALAPPDATA`/`DSH_HOME` 钉扎保留为纵深防御。
- discovery 可证明只读：inspection helper 复用的是一次真实启动所读的同一批读取，跳过全部写入路径；测试钉死了 manifest、两级 patch 层（profile 与 home）与目录集合在 inspection 前后字节不变，missing home 保持不被创建。
- 桌面端绝不自行分类 profile：每个状态都来自官方 CLI 文档；`web-capable`/`headless` 要求官方 row id 搭配官方插件名，每个条目自带 evidence 或 error 行，供后续选择界面使用。
- 凭据形态文本无法从失败路径逃逸：CLI 在进入 JSON 或 stderr 前脱敏，桌面端再对每条 `ProfileDiscoveryError` 与解析出的 `error` 字段二次脱敏。
- 损坏或手改的状态在启动时报出文件名与字段路径，而不是污染用户选择；原子替换保证写入中途崩溃时旧状态完好。
- 本包仍然排除：Runtime Lens、memory/compaction editor、benchmark、A/B experiment、完整 Workbench conversation renderer、tray、自动更新、UI 框架或状态管理依赖、第二 launcher/profile/runtime 状态源，以及对官方 Harness Web UI 的任何视觉重写；desktop 仍然绝不自行判断 Web-capability。

## B1 finalize gate（fix/b1-finalize）

集成到当前 main 时补上三项收尾改动：

- **晋升核实后才复用 discovery 缓存。**`choose-existing-profile` 不再把 `phase === 'running'` 当作目标启动成功的证明：失败的 Existing 切换回退 lastKnownGood 后同样是 `running`（且 `recovered: true`），而磁盘上的 `active` 已经回到旧 Home。调度器现在只有在 controller 处于 running 且非 recovered、并且持久化的 `active` 与请求的 selection 完全一致（`launcher-state.ts` 的 `sameHarnessSelection`）时才复用候选的 discovery；其余任何结果都清空候选缓存、按实际持久化的 active Home 重新只读 discovery——profile 面板绝不可能拿一个 Home 的列表配另一个 Home 的运行时。
- **同一套流式安全脱敏规则。**删除 `dsh-service.ts` 内只认单一形态的私有脱敏器；`redact.ts` 是凭据规则的唯一来源，并新增 `createStreamingRedactor`，其不变式是与 chunk 边界无关：对每个受支持形态的每个切分点（包括凭据在 chunk 尾部已达最短合法长度、下一 chunk 继续 body 的情况），流式输出拼接与整段 `redactSecrets` 完全一致；扣留缓冲有上限，病态超长 token run 强制脱敏落盘并吞掉残余。服务日志写入器经 `StringDecoder` 喂入，多字节 UTF-8 被 chunk 拆开也不破坏。
- **发行构建必出自当前源码。**公开的 `build:desktop-dist` 现在先串起 `build:lib:host`、`build:web`、`build:desktop`，再进入内部的 `build:desktop-dist:assemble`，打包发行物永远来自当前检出的源码；`requirePrerequisites` 只保留为纵深防御，单测门禁（`tests/build-scripts.spec.ts`）钉死链条的存在与顺序。

### 上游改动债与出口（记录在案）

B1 为 profile inspection 修改了上游命名空间：`apps/cli`（`dsh profiles --json`）与 `packages/boot/app-boot`（`inspect.ts`、`patches.ts` 及导出的 inspection helper）。这些属于通用 Harness 能力——上游 delta，不是 DeepSeekGUI 产品逻辑——B1 阶段刻意原地保留、不做搬迁。出口二选一：（1）向 DeepSeek Harness 上游提议合入；（2）上游不接受则抽入 DeepSeekGUI Core / upstream-adapter 层。自 B2 起，DeepSeekGUI 专属产品逻辑不得再进入 `@deepseek-ai/*` 命名空间；新产品能力放进 DeepSeekGUI 自有包。
