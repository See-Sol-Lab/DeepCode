# Agent Note: DeepCode harness home and launcher selection core

Status: implemented

English | [中文](2026-08-16-deepcode-native-harness-control-plane.zh.md)

## Problem

The desktop shell had no durable notion of "which Harness home and which profile to launch": `--profile web` was hardcoded inside `resolveDshLaunch`, the packaged app fixed `DSH_HOME` to `userData/dsh` (overridable by an environment variable), and dev inherited the ambient environment. A future control plane — a launcher selection UI, pending/last-known-good recovery semantics, more profiles — needs one persisted selection as its single source of truth, with a schema that fails loudly instead of silently rewriting user state.

## Decision

`apps/desktop/src/launcher-state.ts` defines the launcher state and its store. `HarnessHomeRef` is a closed union: `managed` (resolved at runtime to `join(userData, 'dsh')`, never touching a global `~/.dsh`) or `existing` (an explicit absolute path only, preserved verbatim including spaces and Unicode, never created, migrated, or merged). `HarnessSelection` pairs a home reference with a profile name; `LauncherStateV1` is `schemaVersion: 1` plus `active`, `pending`, `lastKnownGood`, and `lastBootFailure` (fixed `null` until a later package widens it to `BootFailure | null`, so that change adds no field and migrates nothing). The profile is a plain string checked against the same name rules as `@deepseek-ai/dsh-app-boot`'s `resolveProfileDir`: non-empty, no `/` or `\`, and not `.`, `..`, or `node_modules`. `headless`, `tui`, custom names, and spaces/Unicode names are all valid at the schema layer; whether a profile is Web-capable is left to later discovery/control and is never decided here. The default stays managed + `web`.

The state lives exclusively in `launcher-state.json` under Electron userData and is never written inside `DSH_HOME`. `LauncherStateStore.read()` returns the default state (managed + web, empty pending/last-known-good/last-boot-failure) when the file is absent — the new-user path — and does not create it; invalid JSON, an unknown `schemaVersion`, unknown fields, or invalid field values (an invalid profile name, non-absolute `existing.path`, a non-null `lastBootFailure`, extra keys anywhere) throw `LauncherStateError` with a field-pathed message instead of falling back or overwriting. `write()` validates the state through the same strict parser via a JSON round-trip, serializes to a stable key order (2-space indent, trailing newline), and replaces the file atomically with a same-directory temp file + `rename`, cleaning up the temp file on failure.

`resolveDshLaunch` in `dsh-service.ts` no longer hardcodes `--profile web` and no longer takes a packaged-only `packagedDshHome`: it takes explicit required `profile` and `dshHome`. Dev and packaged share one entry — the `@deepseek-ai/dsh` bin (`apps/cli/src/bin.ts` through tsx in dev, `resources/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js` under `ELECTRON_RUN_AS_NODE` when packaged) — and one fixed `--host 127.0.0.1 --port 3080`. Both forms inject `DSH_HOME` from the selection; the `DSH_HOME` environment variable no longer overrides it. `main.ts` reads the store at startup, launches with `state.active`, and fails with an understandable dialog when the state file is invalid. Single-instance lock, loopback-only serving, log redaction, and Windows process-tree cleanup are unchanged.

Profile inspection ships as a boot-free, read-only surface. `@deepseek-ai/dsh-app-boot` exports `inspectExistingProfile`, `inspectExistingProfiles`, and `classifySurface`: the helpers reuse the official manifest read, two-anchor bundle resolution, patch parsing (`loadOptionalPatches`/`loadOverlayPatches`), and empty-root composition, and compose the complete static composition in real-boot layer order — bundle patches, the profile's own `cordis.patch.yml`, then the home-level `$DSH_HOME/cordis.patch.yml` (absent means an empty layer, never created) — while never calling `initProfile`, `normalizeShippedProfile`, `healProfilesModuleFallback`, or `writeProfileManifest`, and never generating or rewriting `cordis.yml`. `dsh profiles --json` prints one document — `schemaVersion: 1`, the resolved `DSH_HOME`, and per-profile `name`/`dir`/`bundles`/`staticStatus`/`evidence` (or `error` for malformed) — with stdout carrying only the JSON and diagnostics on stderr; a missing home or `profiles` directory yields an empty list and creates nothing. Static status is `web-capable` only when the official `web-startup`/`webserver`/`web-runtime` rows carry their official plugin names (`@deepseek-ai/dsh-web-app/startup`, `@deepseek-ai/dsh-host-webserver`, `@deepseek-ai/dsh-web-app`) and none is literally `disabled: true`; `headless` is the same check for `headless-startup`/`headless-runner` (`@deepseek-ai/dsh-headless/startup`, `@deepseek-ai/dsh-headless`); `malformed` means that profile's inspection threw; everything else is `candidate`. Literal `disabled: true` counts as off, non-literal dynamic `disabled`, custom plugin names under official ids, and custom surfaces are never guessed, and boot-failing is left to a real launch. One broken profile — or a broken home patch layer, which every profile reads — becomes per-profile `malformed` entries and never fails the whole home. Every failure message is credential-redacted before it reaches the JSON `error`, CLI stderr, or the desktop: API keys (`sk-…`), GitHub tokens (`gh*_…`), Slack tokens (`xox*…`), AWS access-key ids (`AKIA…`), and Bearer tokens each keep their prefix with a `<redacted>` suffix. The desktop's `apps/desktop/src/profile-discovery.ts` runs the same DSH entry/env construction the launcher boots (`resolveDshCommand`) with `profiles --json` and strictly validates the document (unknown schema or fields rejected, `malformed` requires a non-empty `error`, non-`malformed` must not carry one) — no YAML dependency and no second parser; it collects child stdout/stderr as UTF-8 streams (`setEncoding`), so a multibyte character split across pipe chunks still reassembles.

The restart boundary and last-known-good recovery live in `apps/desktop/src/harness-controller.ts`. `HarnessController` owns the switching protocol over the launcher state and an in-memory runtime status with seven phases — `idle`, `starting` (an initial start or restart boot), `switching` (a new selection's boot), `recovering` (a last-known-good fallback boot), `stopping` (entered synchronously the moment stop is requested), `running`, and `failed` — and coordinates only launcher state, selection resolution, spawn/HTTP-readiness/page-load, and stop; it owns no Harness settings, sessions, credentials, or plugins. `switchTo(selection)` atomically persists `pending` (active and last-known-good untouched), fully stops the current process tree, then boots the pending selection; only after spawn, HTTP readiness, and `loadURL` all succeed does it promote pending to active AND last-known-good and clear pending. On failure it stops the failed process, records a length-capped, credential-redacted `lastBootFailure` (`stage` ∈ `spawn`/`readiness`/`page-load`; an empty error message falls back to a staged default text, and the schema rejects messages over 512 characters), clears pending, and tries last-known-good exactly once — success surfaces `recovered: true` and keeps the persisted failure as the switch's evidence (only the next fully successful switchTo/restart clears it; an ordinary start leaves it intact), failure leaves the in-memory status `failed` with no loop. A pending read at startup is an interrupted switch: it is cleared (never auto-continued) and the boot uses last-known-good ?? active. Every fully successful boot through the same three gates — `start()` (active or the recovered LKG), a switch promotion, and `restart()` — writes the booted selection as last-known-good, so a user who has never switched still has a fallback for their first bad switch. `restart()` reboots active only — no pending, no Home/Profile change, no recovery on failure — and its success is what clears an old `lastBootFailure` together with the next successful switch promotion. `stop()` flags shutdown synchronously and enters `stopping` immediately, killing the child so an in-flight readiness wait, page load, or fallback terminates promptly: window close records no new failure, runs no fallback, promotes nothing, and never continues the boot, the already-written `pending` stays on disk for the next start's interrupted-switch rule (no forged success or failure is written on exit), the process tree is cleaned exactly once, and the final status is `idle`. `LauncherStateV1.lastBootFailure` widened from the P1 fixed `null` to `BootFailure | null` on the same `schemaVersion: 1` (no added or migrated field), and `BootFailure` carries an optional `selection` naming the selection that failed to boot, so old state files still parse. All public operations serialize through one queue, so concurrent calls run in arrival order and repeated stops share one in-flight cleanup; the main-process runtime adapter keeps one stop → restart-safe lifecycle with the fixed loopback, port probe, log redaction, Windows `taskkill /T /F`, and the packaged no-Node/no-pnpm path unchanged, and hangs an unexpected-exit watcher on every newly spawned child (suppressed while a boot is still in flight and for deliberate stops), so switchTo/restart children are never unwatched.

The control surface is DeepCode's integrated Desktop Chrome: the window hides the system title bar (`titleBarStyle: 'hidden'` with a Windows `titleBarOverlay` keeping the native minimize/maximize/close buttons), and two `WebContentsView`s compose the content — the Compatibility View hosting the untouched official Web UI below a 47px top bar, and above it a trusted local chrome renderer (`src/chrome/`: static HTML/CSS + `renderer.ts` + a CommonJS sandboxed preload) drawing the always-visible hamburger button, the quiet centered page title (hidden below ~900px width), and the clickable Harness status pill. Both the hamburger's Harness entry and the pill open the same Harness panel; the two entries share one model and one action path. Data flows one way: launcher-state + `HarnessController` (a new `onStatusChanged` callback funnels every `setStatus` transition) + read-only discovery → main builds a serializable `DesktopControlModel` (`control-model.ts`) → the narrow `window.deepCodeDesktop` preload API (`getControlModel` / `runControlCommand` / `onControlModelChanged` / `setChromeExpanded`; no generic IPC) → the chrome renderer, whose only local state is pure UI (open panel, focus return target). User actions come back as a closed `DesktopControlCommand` union that main validates with `parseControlCommand` (unknown types, extra keys, and illegal profile names are rejected) and routes through `control-dispatch.ts` to the existing controller/discovery paths; the renderer never reads launcher JSON, never spawns, and never judges recovery. The full DSH_HOME path appears only inside the panel (single-line ellipsis, full value on hover), never across the top bar. Status-pill mapping is live during switches: grey idle/stopping, blue starting/switching, yellow recovering and running-recovered, green running, red failed. Chinese strings serve zh locales from a static dictionary with English fallback; keyboard access covers Tab focus, Enter/Space activation, Escape-to-close with focus return, and visible focus rings, with the drag region declared on the bar and `no-drag` on every interactive control. Menu-open expansion is bounds-managed by main (`setChromeExpanded` swaps the chrome view between bar-height and full-window; window resize relayouts both views event-driven, no polling). Profile items follow the discovery status: `web-capable` entries are directly selectable (checked when active), `candidate` entries stay selectable with a Try/Unverified label, and `headless`/`malformed` entries are disabled with their reason; a persisted failure whose `selection` matches a listed profile marks that item boot-failing with its stage. Choose Existing Home is `showOpenDialog` (openDirectory) → read-only discovery of that directory → an in-panel profile choice (`choose-existing-profile`) → one `controller.switchTo({ home: { kind: 'existing', path }, profile })`; every cancel step (`cancel-existing-home` included) writes nothing and no half-state is ever saved. Use Managed Home calls `controller.switchTo({ home: { kind: 'managed' }, profile: 'web' })` and refreshes the discovery cache. Every switch/restart goes through the P3 controller. Recovery Details renders inline in the panel — only the failure stage, the length-capped redacted message, the failed target, the recovery target, and the diagnostics log path. Both views keep `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; the Compatibility View carries the loopback-only navigation and external-link policy, the chrome view denies all navigation and new windows, and the old root-level English application menu is gone (`Menu.setApplicationMenu(null)`).

Desktop Chrome follows `ui-theme.preference` and `locale.preference` from the active Harness Home. Main reads both fields from one `settings.yaml` snapshot and watches that Home's directory so atomic replacements remain observable. It re-reads and reattaches after the first boot, when a fresh Managed Home has been created, and after a Managed/Existing Home change; the official page, status pill, tray, dialogs, and terminal therefore share the active Home's explicit preference instead of retaining the Windows fallback or the previous Home's value.

Third-party Cordis plugin support is proven by a keyless e2e, not implemented in production. `apps/desktop/tests/fixtures/native-proof-plugin` is a minimal third-party-style Cordis function plugin (package name `deepcode-native-proof-plugin`, not a workspace package): production code never imports it and the packaged runtime never treats it as built-in — it mounts only because a test-built profile lists it. Its sole observable effect comes from `apply(ctx, config)`: it writes a JSON marker (nonce, plugin name, pid, ppid, `DSH_HOME`) and can deliberately throw or serve a loopback readiness gate. `apps/desktop/tests/native-plugin-proof.e2e.ts` stages a real Existing `DSH_HOME` (profiles manifest + `cordis.patch.yml` insert row + a profile-local `node_modules/deepcode-native-proof-plugin`, copied into place — no `pnpm install`), then proves: boot-free discovery produces no marker; a launch through the launcher's own vector (`resolveDshCommand` → official dsh boot → profile composition) mounts the fixture, and the marker's pid equals the actual DSH child pid, its `DSH_HOME` equals the Existing Home, and its nonce matches the one passed through the plugin row's config; removing the insert row produces no marker; a deliberate apply-throw makes the pending boot fail and the controller falls back to last-known-good (`recovered: true`, `lastBootFailure.stage: 'readiness'`, selection pointing at the failed profile); and profile manifest, patch, and fixture files stay byte-identical across discovery and boots. No model is called and no API key is required. The fixture is test data preparation, not production copy logic: DeepCode understands nothing about the marker and never writes one.

B1 closes with the packaged Windows acceptance (`apps/desktop/tests-e2e/packaged-acceptance.e2e.ts`, run by `test:desktop-parity`), which drives `dist/desktop/win-unpacked/DeepCode.exe` directly in an isolated temp root containing spaces and Unicode. Case A proves a fresh install boots Managed/web and lands the default state (active == lastKnownGood == managed/web, pending and lastBootFailure null); Case B switches and restarts between two web-capable profiles of an Existing Home through the production control entry — real DOM clicks on the Desktop Chrome (status pill → Harness panel → stable element ids `harness-switch-profile` / `harness-profile-<name>` / `harness-restart`), executed inside the chrome view's webContents via Electron main-process evaluate; Case C repeats the P5 plugin proof inside the packaged exe (marker ppid equals the Electron main pid, marker pid differs — the `ELECTRON_RUN_AS_NODE` DSH child); Case D proves the apply-throw switch falls back to last-known-good with the failure persisted (`stage: 'readiness'`, selection pointing at the broken profile, the Harness panel's inline Recovery Details present); Case E proves the selection survives close and relaunch; Case F proves DeepCode never copies, migrates, or rewrites profile definitions, the third-party package, or sentinels — official Harness may still maintain its own `cordis.yml` and `profiles/node_modules` fallback during real boots — and that a discovery-only run is byte- and tree-identical before and after, with the Existing sentinel never appearing under the Managed Home. The packaged exe also boots with only `C:\Windows\System32` on PATH (no external Node/pnpm), and close releases port 3080 with no residual processes. No model is called and no API key is required anywhere in the acceptance.

## Alternatives considered

- **A JSON schema library (zod or similar)**: rejected — the desktop package ships with no runtime dependencies; a hand-written strict validator is roughly a hundred lines and keeps every failure message field-pathed and in Chinese.
- **Falling back to the default on an invalid file**: rejected — reading a corrupted file as "first run" silently discards the user's existing selection; a later overwrite would destroy it for good. Failing loudly and letting the user repair or delete the file preserves their data.
- **Keeping the `DSH_HOME` environment override**: rejected — two sources of truth for one launch fact. The selection is the only source; test isolation keeps working because the parity environment redirects `APPDATA` itself.
- **A `['web']` profile allowlist in the state schema**: rejected — the state records a launch selection, not launch capability; Web-capability discovery is a later package's job, and persisting any custom profile name would otherwise need a schema change first. The schema checks only the official profile-name rules.
- **Re-implementing discovery inside Electron** (a desktop-side profile parser or YAML dependency): rejected — the desktop runs the official CLI's `profiles --json` through the same entry and env construction it boots, so classification reuses the harness's own manifest, bundle, and patch semantics rather than a desktop-side copy; a disagreement between the two surfaces as a schema failure instead of a silent misclassification.

## Consequences

- New users keep the same default launch (managed + web); the dev run now resolves `DSH_HOME` through the same selection path instead of inheriting the ambient environment.
- The v1 record already carries `lastBootFailure: null`, so a later package can widen the field type to `BootFailure | null` without adding or migrating a field; the strict parser rejects any non-null value today.
- The parity and packaged-acceptance e2e isolate Electron userData through the Chromium-standard `--user-data-dir` switch (Windows resolves userData through the Known Folder API and ignores `APPDATA`); `APPDATA`/`LOCALAPPDATA`/`DSH_HOME` pinning stays as defense in depth.
- Discovery is provably read-only: the inspection helpers reuse the same reads a boot makes and skip every write path; tests pin that manifests, both patch layers (profile and home), and the directory set are byte-identical before and after, and that a missing home stays uncreated.
- The desktop never classifies profiles itself: every status comes from the official CLI document, `web-capable`/`headless` require the official row ids with the official plugin names, and each entry carries evidence or error lines for the future selection surface.
- Credential-shaped text cannot escape a failure path: the CLI redacts before JSON or stderr, and the desktop redacts again on every `ProfileDiscoveryError` and parsed `error` field.
- Corrupted or hand-edited state fails startup with a named file and field path rather than corrupting the user's choice; atomic replacement means a crash mid-write leaves the previous state intact.
- What this package still excludes: no Runtime Lens, memory/compaction editor, benchmark, A/B experiment, full Workbench conversation renderer, tray, auto-update, UI framework or state-management dependency, second launcher/profile/runtime truth store, or any visual rewrite of the official Harness Web UI; the desktop still never judges Web-capability itself.

## B1 finalize gate (fix/b1-finalize)

The integration onto current main added three closing changes:

- **Promotion-verified discovery-cache reuse.** `choose-existing-profile` no longer treats `phase === 'running'` as proof the target booted: a failed Existing switch that recovers to last-known-good is also `running` (with `recovered: true`) while the persisted `active` has already returned to the old Home. The dispatcher now reuses the candidate's discovery only when the controller is running non-recovered AND the persisted `active` equals the requested selection (`sameHarnessSelection` in `launcher-state.ts`); every other outcome clears the candidate cache and re-runs read-only discovery against the actual persisted active Home, so the profile panel can never show one Home's list against another Home's runtime.
- **One streaming-safe redaction rule set.** The private single-pattern redactor inside `dsh-service.ts` is gone; `redact.ts` is the only source of credential rules and now ships `createStreamingRedactor`, whose invariant is chunk-boundary independence: concatenated streaming output equals one whole-text `redactSecrets` pass for every split point of every supported family (including a secret that already reaches minimum legal length at a chunk end and keeps extending in the next chunk), with a bounded pending buffer that force-redacts and swallows pathological over-long token runs. The service log writer feeds it through a `StringDecoder`, so multibyte UTF-8 split across chunks stays intact.
- **Current-source distribution builds.** The public `build:desktop-dist` now chains `build:lib:host`, `build:web`, and `build:desktop` before the internal `build:desktop-dist:assemble` step, so the packaged distribution always comes from the checkout as it is now; `requirePrerequisites` remains as defense in depth only, and a unit gate (`tests/build-scripts.spec.ts`) pins the chain's presence and order.

### Upstream delta and exit path (recorded debt)

B1 modified upstream namespaces for profile inspection: `apps/cli` (`dsh profiles --json`) and `packages/boot/app-boot` (`inspect.ts`, `patches.ts`, exported inspection helpers). These are generic Harness capability — an upstream delta, not DeepCode product logic — and deliberately stay in place for B1 rather than being relocated now. The exit is one of two: (1) propose them upstream to DeepSeek Harness; (2) if upstream declines, extract them into DeepCode Core / an upstream-adapter layer. From B2 onward, DeepCode-specific product logic must not be added to `@deepseek-ai/*` namespaces; new product capability goes into DeepCode-owned packages.
